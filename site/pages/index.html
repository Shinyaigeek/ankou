You have a spec, a PDF, a long post. What you want out of it is not always the text, top to bottom.

kamu takes the sources and what you want out of them, picks the shape, and gives it back as something you can actually read — a flipbook, a deck, a quiz you have to pass, four seconds of kinetic type. One command, or one call from your agent.

Start here

Three commands and a document

Node 22+. No build step, no config file to write, no account to make.

  1. Install the CLI

    The unscoped kamu on npm is an unrelated package, hence the scope — what it installs is still kamu.

  2. Point it at a model

    Any of four providers, or none of them: kamu providers says which are ready on this machine and what the rest are missing. All the routes →

  3. Say what you want out of it

    The intent is the brief, in whatever language you think in. It is what the planner reads to pick a shape — and --plan-only shows you that decision before you pay for the generation. 

# the CLI, globally
npm i -g @shinyaigeek/kamu

# the SDK, in a project
npm i @shinyaigeek/kamu-core

# or from a checkout — also how you develop on it
git clone https://github.com/Shinyaigeek/kamu.git
cd kamu && ./scripts/install-local.sh
# whichever you have — the first key found wins
export ANTHROPIC_API_KEY=sk-...
# or: --provider claude-code   a Claude Code subscription, no key
# or: --provider openai        OpenAI, OpenRouter, LM Studio, vLLM, Groq
# or: --provider ollama        local, free, no network egress

kamu providers
kamu spec.md -i "一字一句漏らさず頭に入れたい"
# → flipbook: plays the text back one character at a time, verbatim

kamu https://example.com/post -i "I need to remember this" --play
# → quiz, in your terminal

kamu paper.pdf notes.md -i "explain it like I have never seen it"
# → dialogue: two voices working through it

Sources are file paths, URLs, or - for stdin. Markdown, text, HTML and PDF are understood; a URL is fetched and stripped down to the readable part, so navigation and cookie banners do not end up in your flipbook.

How it works

One model call, many surfaces

Ingest normalises the sources without rewriting them. The planner reads your intent and picks the shape. Compose fills a format-specific schema. Rendering is a pure function after that.

sourcesmd, txt, html, pdf, url, stdin
ingesttext, headings, language — never rewritten
planan LLM reads your intent and picks the shape
composean LLM fills a format-specific schema
Piecetyped JSON — the thing worth keeping
renderhtml · tui · json

The middle artefact is a Piece: a typed, format-specific structure. Renderers are pure functions of a Piece, so the same chewed result can be played in a terminal, opened in a browser, or handed to another program as JSON without asking the model to do the work twice.

Long documents are windowed, mapped per window and reduced, so a 200-page PDF and a 400-word post go down the same path. Where a provider supports tool use or structured output, kamu uses it; where it does not, output is parsed, validated, and handed back with its own errors once. 

# pay the model once…
kamu paper.pdf -i "覚えたい" --render json -o piece.json

# …and render it as often as you like
kamu render piece.json --open
kamu render piece.json --play

kamu render touches no model and no network. The HTML it writes is one self-contained file: no CDN, no fonts to fetch, no build step. It works offline, follows the reader's colour scheme, prints sensibly, and you can mail it to someone.

The interesting constraint

The flipbook never paraphrases

For a format whose whole promise is 一字一句 — every character — you cannot let a language model write the body. So it doesn't.

The model gets to produce annotations only: chapter titles, terms worth emphasising, readings for hard words, and a reading pace. The text itself is sliced verbatim out of the source and exploded into grapheme clusters by the renderer.

Fidelity is structural, not a promise the model has to keep.

The same instinct runs through the rest of it: the planner's menu is generated from the format registry, so a format cannot exist and be invisible to it, and a knob cannot be declared and silently unsettable.

Wiring up a provider →

agents

It was built to be called by something else

A Piece is plain JSON and rendering is pure, so an agent can decide the shape, store the structure, and re-render it on any surface later — with progress events, cancellation, and errors that carry a hint.

kamu as a tool call →

internals

No runtime dependencies

Providers are fetch calls; the HTML extractor, the JSON Schema validator and the terminal layer are all in-tree. PDF and the Claude Agent SDK are optional peers, imported lazily.
